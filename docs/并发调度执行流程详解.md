## 2. 思维链一：消息入口的决策树

**场景**：新消息 M 到达 Worker

```
消息 M 到达
    │
    ▼
┌─────────────────────────────────────┐
│ Q1: StagingArea[AnchorID] 存在吗？   │
└─────────────────────────────────────┘
    │
    ├── 存在 ──────────────────────────────────────────────┐
    │   │                                                  │
    │   │  【思考】该 Anchor 有未处理的消息堆积              │
    │   │  可能原因：                                       │
    │   │  - 正在异步加载 Entity (LoadingAnchors=true)     │
    │   │  - 锁竞争失败，等待重试                           │
    │   │                                                  │
    │   │  【决策】保持 FIFO，追加到队尾                     │
    │   │                                                  │
    │   ▼                                                  │
    │  StagingArea[AnchorID].PushTail(M)                   │
    │  return (不执行，等待统一调度)                         │
    │                                                      │
    └── 不存在 ────────────────────────────────────────────┐
        │                                                  │
        │  【思考】该 Anchor 当前空闲，可以立即尝试执行       │
        │                                                  │
        ▼                                                  │
    执行 TryProcessAnchor(M)                               │
        │                                                  │
        ├── Result_Success ─────────────────────────────── │ ──► 完成
        │                                                  │
        ├── Result_LockBusy ────────────────────────────── │ ──┐
        │   │                                              │   │
        │   │  【思考】锁竞争失败，消息已被放入队首           │   │
        │   │  需要标记该 Anchor 待重试                     │   │
        │   │                                              │   │
        │   ▼                                              │   │
        │  RetryList.Add(AnchorID)                         │   │
        │  // M 已在 TryProcessAnchor 中入队首              │   │
        │                                                  │   │
        └── Result_NeedIO ─────────────────────────────────│───┘
            │                                              │
            │  【思考】Entity 不在内存，需要异步加载         │
            │  已在 逻辑单元四 中处理                        │
            │                                              │
            ▼                                              │
           完成 (等待 AsyncComplete 事件)                   │
```

## 3. 思维链二：TryProcessAnchor 的加锁序列

**场景**：消息 M 涉及 Entity [A, B, C]（已排序）

```
TryProcessAnchor(M) 开始
    │
    │  【关键设计】按固定顺序加锁，避免死锁
    │  排序后: A < B < C
    │
    ▼
┌─────────────────────────────────────┐
│ Step 1: TryLock(A)                  │
└─────────────────────────────────────┘
    │
    ├── 失败 ──► 无需回滚（没有持有任何锁）
    │            M 入 StagingArea[A] 队首
    │            return Result_LockBusy
    │
    └── 成功 ──► 持有锁: {A}
                 │
                 ▼
         ┌─────────────────────────────────────┐
         │ Step 2: TryLock(B)                  │
         └─────────────────────────────────────┘
             │
             ├── 失败 ──► 回滚: Unlock(A)
             │            M 入 StagingArea[A] 队首
             │            return Result_LockBusy
             │
             └── 成功 ──► 持有锁: {A, B}
                          │
                          ▼
                  ┌─────────────────────────────────────┐
                  │ Step 3: TryLock(C)                  │
                  └─────────────────────────────────────┘
                      │
                      ├── 失败 ──► 回滚: Unlock(B), Unlock(A)
                      │            M 入 StagingArea[A] 队首
                      │            return Result_LockBusy
                      │
                      └── 成功 ──► 持有锁: {A, B, C}
                                   │
                                   ▼
                           ┌─────────────────────┐
                           │ 执行业务逻辑        │
                           └─────────────────────┘
                                   │
                                   ▼
                           Unlock(C), Unlock(B), Unlock(A)
                           return Result_Success
```

**设计要点**：

| 问题 | 答案 |
|------|------|
| 为什么用 Anchor（最小 ID）入队？ | 保证同一组 Entity 的消息总是进入同一个暂存队列，维护 FIFO 顺序 |
| 为什么回滚时释放所有锁？ | 避免持有部分锁导致其他消息饥饿 |
| 为什么入队首而不是队尾？ | 该消息是"正在执行但失败"的，优先级应高于"等待执行"的消息 |

## 4. 思维链三：异步加载的状态流转

**场景**：消息 M 需要 Entity A，但 A 不在内存

```
时间线 ──────────────────────────────────────────────────────────────────►

     T1                    T2                    T3                    T4
     │                     │                     │                     │
     ▼                     ▼                     ▼                     ▼
┌─────────┐          ┌─────────┐          ┌─────────┐          ┌─────────┐
│ 消息 M  │          │ 消息 M2 │          │ AsyncLoad│          │执行 M   │
│ 到达    │          │ 到达    │          │ 完成    │          │执行 M2  │
└─────────┘          └─────────┘          └─────────┘          └─────────┘
     │                     │                     │                     │
     ▼                     ▼                     ▼                     ▼

【T1 状态变化】
LoadingAnchors[A] = false → true
StagingArea[A] = [] → [M]
RetryList 不包含 A
触发 EntityManager.AsyncLoad(A)

【T2 状态变化】
发现 StagingArea[A] 存在
StagingArea[A] = [M] → [M, M2]  // FIFO 追加
不触发新的加载（已在加载中）

【T3 状态变化】
收到 EventAsyncComplete(A)
LoadingAnchors[A] = true → false
Pop M from StagingArea[A]
执行 TryProcessAnchor(M)
  └─ 成功 → StagingArea[A] = [M2] //队列非空，还有M2消息
           RetryList.Add(A)  // 加入重试

【T4 状态变化】（在 RetryProcess 中）
从 RetryList 取出 A
Pop M2 from StagingArea[A]
执行 TryProcessAnchor(M2)
  └─ 成功 → StagingArea[A] = []
           删除 StagingArea[A]
           RetryList.Remove(A)
```

### 4.1 关键设计：LoadingAnchors 与 RetryList 的互斥状态

在设计中，一个 AnchorID 在同一时刻只能处于以下状态之一：

| 状态 | LoadingAnchors[A] | A ∈ RetryList | 含义 |
|------|-------------------|---------------|------|
| 空闲 | false | false | 无堆积消息 |
| **IO 等待** | **true** | **false** | 正在异步加载，不在重试列表 |
| 锁竞争等待 | false | true | 等待重试获取锁 |

**为什么 NeedIO 时不加入 RetryList？**

```go
// 逻辑单元四: LoadEntities
func LoadEntities(msg Message, anchorID AnchorID, refs []EntityRef) {
    StagingArea.PushHead(anchorID, msg)
    LoadingAnchors[anchorID] = true   // 标记 IO 状态
    // 注意：这里不加入 RetryList
    // 因为 RetryProcess 会检查 LoadingAnchors，跳过正在加载的 Anchor
    EntityManager.AsyncLoad(refs, callback)
}
```

**原因**：
1. RetryProcess 遍历 RetryList 时会跳过 `LoadingAnchors[A] == true` 的项
2. 如果加入 RetryList，每次 Tick 都会无效遍历这个项
3. 等 AsyncComplete 时再加入更高效

### 4.2 Anchor 状态转换图

```
                    ┌──────────────┐
                    │   空闲状态    │
                    │ StagingArea  │
                    │   为空       │
                    └──────┬───────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
    ┌───────────┐    ┌───────────┐    ┌───────────┐
    │  Success  │    │ LockBusy  │    │  NeedIO   │
    │  直接完成  │    │           │    │           │
    └───────────┘    └─────┬─────┘    └─────┬─────┘
                           │                │
                           ▼                ▼
                    ┌───────────┐    ┌───────────┐
                    │ RetryList │    │ Loading   │
                    │  .Add(A)  │    │ Anchors   │
                    │           │    │  [A]=true │
                    └─────┬─────┘    └─────┬─────┘
                          │                │
                          │                │ AsyncComplete
                          │                ▼
                          │          ┌───────────┐
                          │          │ 处理队首  │
                          │          │ 消息 M    │
                          │          └─────┬─────┘
                          │                │
                          │                │ 队列仍非空？
                          │                ▼
                          │          ┌───────────┐
                          └─────────►│ RetryList │ ← 此时才加入
                                     │  .Add(A)  │
                                     └───────────┘
```

**设计要点**：

| 问题 | 答案 |
|------|------|
| 为什么 IO 等待和锁竞争等待是互斥状态？ | 避免 RetryProcess 无效遍历正在加载的 Anchor |
| AsyncComplete 后为什么要检查队列？ | 加载期间可能有新消息到达，需要继续处理 |
| 为什么 AsyncComplete 后才加入 RetryList？ | 此时 LoadingAnchors 已清除，需要新的调度机制驱动后续消息处理 |

## 5. 思维链四：锁竞争的活锁预防

**场景**：Worker1 处理 M1(A,B)，Worker2 处理 M2(A,C)，同时竞争锁 A

```
        Worker1                              Worker2
           │                                    │
           ▼                                    ▼
    TryLock(A) 成功                       TryLock(A) 失败
    持有锁: {A}                           │
           │                              │ 【回滚】
           ▼                              │ M2 入 StagingArea[A]
    TryLock(B) ...                        │ return LockBusy
           │                              │
           ▼                              ▼
    执行业务逻辑                     ┌─────────────────────────┐
           │                        │ 设置 CooldownSet.Add(A) │
           ▼                        │ 当前 Tick 跳过 A        │
    Unlock(B), Unlock(A)            └─────────────────────────┘
           │                                    │
           │                                    │
    ═══════│════════════════════════════════════│═══════ Tick 边界
           │                                    │
           ▼                                    ▼
    处理其他消息                         CooldownSet.Clear()
                                        RetryProcess 取出 A
                                        TryProcessAnchor(M2)
                                               │
                                               ▼
                                        TryLock(A) 成功 ✓
```

**设计要点**：

| 问题 | 答案 |
|------|------|
| 为什么需要冷却机制？ | 如果立即重试，Worker2 可能再次与 Worker1 竞争，形成活锁 |
| 冷却粒度是什么？ | Tick 级别：简单有效，一个调度周期后自动解除 |
| 为什么不用指数退避？ | 游戏服务器对延迟敏感，一个 Tick 的冷却足够让持锁方完成 |

## 6. 思维链五：RetryProcess 的配额消耗策略

**场景**：RetryList = [A, B, C, D]，配额 N = 2

```
RetryProcess(Quota=2) 开始
    │
    │  剩余配额: 2
    │
    ▼
┌─────────────────────────────────────┐
│ 遍历 RetryList[0] = A               │
└─────────────────────────────────────┘
    │
    ├── LoadingAnchors[A] == true ──► 跳过 (IO 忙)
    │   剩余配额: 2 (不消耗)
    │
    └── LoadingAnchors[A] == false
        │
        ├── CooldownSet.Contains(A) ──► 跳过 (冷却中)
        │   剩余配额: 2 (不消耗)
        │
        └── 可以处理
            │
            ▼
        Pop M from StagingArea[A]
        TryProcessAnchor(M)
            │
            ├── Success ──► 剩余配额: 1
            │               若 StagingArea[A] 为空，从 RetryList 移除 A
            │
            ├── LockBusy ──► 剩余配额: 1
            │                CooldownSet.Add(A) // 惩罚
            │                M 已回滚到队首
            │
            └── NeedIO ──► 剩余配额: 1
                           LoadingAnchors[A] = true
                           触发异步加载
    │
    ▼
┌─────────────────────────────────────┐
│ 遍历 RetryList[1] = B               │
│ ...同上逻辑...                       │
│ 剩余配额: 0                          │
└─────────────────────────────────────┘
    │
    ▼
配额耗尽，退出 RetryProcess
RetryList[2]=C, RetryList[3]=D 留待下次 Tick
```

**设计要点**：

| 问题 | 答案 |
|------|------|
| 为什么用配额？ | 防止 RetryList 过长时阻塞新消息处理 |
| 配额如何消耗？ | 只在实际执行时消耗，跳过不计数，保证公平性 |
| 遍历顺序是什么？ | FIFO：先入 RetryList 的 Anchor 优先处理 |

## 8. 锁机制的完整实现

### 8.1 锁的数据结构设计

```go
// 全局锁表（跨 Worker 共享）
type GlobalLockTable struct {
    mu     sync.Mutex                    // 保护 locks map 的互斥锁
    locks  map[EntityID]*EntityLock      // EntityID -> 锁状态
}

type EntityLock struct {
    holder   WorkerID      // 当前持有者（0 表示无人持有）
    version  uint64        // 锁版本号（用于调试和监控）
}
```

### 8.2 TryLock 的原子操作流程

```
TryLock(EntityID, WorkerID) -> (success bool)
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│ Step 1: 获取全局锁表的互斥锁                                  │
│         GlobalLockTable.mu.Lock()                           │
└─────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│ Step 2: 检查 EntityLock 状态                                 │
│                                                             │
│   lock := GlobalLockTable.locks[EntityID]                   │
│                                                             │
│   if lock == nil {                                          │
│       // 首次加锁，创建锁记录                                 │
│       lock = &EntityLock{holder: 0, version: 0}             │
│       GlobalLockTable.locks[EntityID] = lock                │
│   }                                                         │
└─────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│ Step 3: 尝试获取锁                                           │
│                                                             │
│   if lock.holder == 0 {                                     │
│       // 无人持有，获取成功                                   │
│       lock.holder = WorkerID                                │
│       lock.version++                                        │
│       GlobalLockTable.mu.Unlock()                           │
│       return true                                           │
│   }                                                         │
│                                                             │
│   if lock.holder == WorkerID {                              │
│       // 【异常】同一 Worker 重复加锁，记录错误                │
│       log.Error("reentrant lock detected", EntityID)        │
│       GlobalLockTable.mu.Unlock()                           │
│       return true  // 或 panic，取决于策略                   │
│   }                                                         │
│                                                             │
│   // 被其他 Worker 持有，获取失败                             │
│   GlobalLockTable.mu.Unlock()                               │
│   return false                                              │
└─────────────────────────────────────────────────────────────┘
```

### 8.3 批量加锁的回滚机制

```go
// TryLockMultiple 尝试按顺序获取多个锁
// 返回: (success, failedIndex, heldLocks)
func TryLockMultiple(entities []EntityID, workerID WorkerID) (bool, int, []EntityID) {
    heldLocks := make([]EntityID, 0, len(entities))
    
    for i, entityID := range entities {
        if !TryLock(entityID, workerID) {
            // 加锁失败，回滚已持有的锁
            for j := len(heldLocks) - 1; j >= 0; j-- {
                Unlock(heldLocks[j], workerID)
            }
            return false, i, nil
        }
        heldLocks = append(heldLocks, entityID)
    }
    
    return true, -1, heldLocks
}
```

**状态转换图**：

```
                    TryLock(A, W1)
    ┌─────────┐    success=true     ┌─────────┐
    │ holder=0│ ──────────────────► │holder=W1│
    │(未持有) │                     │ (W1持有)│
    └─────────┘                     └─────────┘
         ▲                               │
         │         Unlock(A, W1)         │
         └───────────────────────────────┘
         
                    TryLock(A, W2)
    ┌─────────┐    success=false    ┌─────────┐
    │holder=W1│ ─────────────────── │holder=W1│
    │ (W1持有)│      (无变化)       │ (W1持有)│
    └─────────┘                     └─────────┘
```

## 9. StagingArea 生命周期管理

### 9.1 数据结构

```go
type StagingArea struct {
    queues map[AnchorID]*MessageQueue   // Anchor -> 消息队列
}

type MessageQueue struct {
    messages  []Message    // 消息列表 (队首在 index 0)
    createAt  time.Time    // 创建时间（用于监控）
}
```

### 9.2 完整的状态机

```
                         ┌─────────────────────────────────────────┐
                         │         StagingArea[AnchorID]          │
                         │              状态机                     │
```

### 9.3 关键操作的伪代码

```go
// PushHead: 消息入队首（用于回滚和首次入队）
func (sa *StagingArea) PushHead(anchorID AnchorID, msg Message) {
    queue := sa.queues[anchorID]
    if queue == nil {
        queue = &MessageQueue{
            messages: make([]Message, 0, 4),
            createAt: time.Now(),
        }
        sa.queues[anchorID] = queue
    }
    // 在队首插入
    queue.messages = append([]Message{msg}, queue.messages...)
}

// PushTail: 消息入队尾（用于新消息追加，保持 FIFO）
func (sa *StagingArea) PushTail(anchorID AnchorID, msg Message) {
    queue := sa.queues[anchorID]
    if queue == nil {
        // 【异常】不应该发生，记录错误
        log.Error("PushTail to non-existent queue", anchorID)
        sa.PushHead(anchorID, msg)
        return
    }
    queue.messages = append(queue.messages, msg)
}

// PopHead: 消息出队首
func (sa *StagingArea) PopHead(anchorID AnchorID) (Message, bool) {
    queue := sa.queues[anchorID]
    if queue == nil || len(queue.messages) == 0 {
        return Message{}, false
    }
    msg := queue.messages[0]
    queue.messages = queue.messages[1:]
    
    // 队列空了，清理
    if len(queue.messages) == 0 {
        delete(sa.queues, anchorID)
    }
    return msg, true
}

// Exists: 检查队列是否存在且非空
func (sa *StagingArea) Exists(anchorID AnchorID) bool {
    queue := sa.queues[anchorID]
    return queue != nil && len(queue.messages) > 0
}
```

```
│                    一致性规则 (INV-1)                                    │
│                                                                         │
│   StagingArea[A] 非空  ⟺  A ∈ RetryList  ∨  LoadingAnchors[A] = true   │

检查点 2: NeedIO 时
┌──────────────────────────────────────────────────┐

┌──────────────────────────────────────────────────┐

┌──────────────────────────────────────────────────┐
│ // 在 PopHead 返回后检查                         │
│ if !StagingArea.Exists(A) {                      │
│     RetryList.Remove(A)     // 从重试列表移除    │
│ }                                                │
└──────────────────────────────────────────────────┘
```

### 10.3 RetryProcess 的完整实现

```go
func (w *Worker) RetryProcess(quota int) {
    processed := 0
    cooldownThisTick := make(map[AnchorID]bool)  // 当前 Tick 的冷却集合
    
    // 创建迭代器，避免遍历中修改问题
    iterator := w.RetryList.Iterator()
    
    for iterator.HasNext() && processed < quota {
        anchorID := iterator.Next()
        
        // 检查 1: IO 忙
        if w.LoadingAnchors[anchorID] {
            continue  // 跳过，不消耗配额
        }
        
        // 检查 2: 当前 Tick 冷却中
        if cooldownThisTick[anchorID] {
            continue  // 跳过，不消耗配额
        }
        
        // 检查 3: 队列为空（防御性检查）
        if !w.StagingArea.Exists(anchorID) {
            w.RetryList.Remove(anchorID)
            continue
        }
        
        // 取出队首消息
        msg, ok := w.StagingArea.PopHead(anchorID)
        if !ok {
            continue
        }
        
        // 消耗配额
        processed++
        
        // 执行
        result := w.TryProcessAnchor(msg)
        
        switch result {
        case Result_Success:
            // 成功，检查队列是否还有消息
            if !w.StagingArea.Exists(anchorID) {
                w.RetryList.Remove(anchorID)
            }
            
        case Result_LockBusy:
            // 失败，消息已回滚到队首
            // 设置冷却，当前 Tick 不再尝试
            cooldownThisTick[anchorID] = true
            
        case Result_NeedIO:
            // 需要加载，消息已入队首
            // LoadingAnchors 已设置
            // 从 RetryList 移除（由 AsyncComplete 重新加入）
            w.RetryList.Remove(anchorID)
        }
    }
}
```

### 12.2 主循环伪代码

```go
func (w *Worker) Run(ctx context.Context) {
    ticker := time.NewTicker(TickInterval)  // 例如 50ms
    defer ticker.Stop()
    
    for {
        select {
        case <-ctx.Done():
            w.shutdown()
            return
            
        case event := <-w.EventChan:
            w.handleEvent(event)
            
        case <-ticker.C:
            w.onTick()
        }
    }
}

func (w *Worker) handleEvent(event Event) {
    switch event.Type {
    case EventType_NewMessage:
        w.ProcessAnchor(event.Message)
        
    case EventType_AsyncComplete:
        w.HandleEventAsyncComplete(event.AnchorID)
        
    case EventType_AsyncError:
        w.HandleEventAsyncError(event.AnchorID, event.Error)
    }
}

func (w *Worker) onTick() {
    // 阶段 1: 处理重试队列
    w.RetryProcess(RetryQuotaPerTick)  // 例如配额 10
    
    // 阶段 2: 清理过期状态（可选）
    w.cleanupStaleStates()
    
    // 阶段 3: 上报指标
    w.reportMetrics()
}
```

### 13.2 告警规则

```yaml
alerts:
  - name: HighLockContention
    condition: rate(LockContention) / rate(LockAcquired) > 0.3
    severity: warning
    message: "锁竞争率超过 30%，可能存在热点 Entity"
    
  - name: StagingAreaBacklog
    condition: StagingAreaSize > 1000
    severity: warning
    message: "暂存区堆积超过 1000 个 Anchor"
    
  - name: DLQNotEmpty
    condition: DLQSize > 0
    severity: critical
    message: "死信队列非空，有消息处理失败"
    
  - name: AsyncLoadSlow
    condition: percentile(AsyncLoadLatency, 99) > 100ms
    severity: warning
    message: "P99 异步加载延迟超过 100ms"
```

## 14. 状态不变式 (Invariants)

设计正确性依赖以下不变式：

| 不变式 | 描述 | 违反后果 |
|--------|------|----------|
| **INV-1** | `StagingArea[A]` 非空 ⟺ A ∈ RetryList ∨ LoadingAnchors[A] | 消息丢失或重复处理 |
| **INV-2** | LoadingAnchors[A] = true ⟹ 存在进行中的 AsyncLoad(A) | 消息永久阻塞 |
| **INV-3** | 任意时刻，每个 Entity 最多被一个 Worker 持有锁 | 数据竞争 |
| **INV-4** | StagingArea[A] 内消息顺序 = 到达顺序 (FIFO) | 消息乱序 |
| **INV-5** | TryLock 序列严格按 EntityID 升序 | 死锁 |

## 15. 边界情况与异常处理汇总

| 场景 | 触发条件 | 处理方式 |
|------|----------|----------|
| 重复 AsyncComplete | 同一 AnchorID 收到两次完成事件 | 检查 LoadingAnchors，忽略第二次 |
| 队列意外为空 | PopHead 时队列已空 | 记录警告日志，清理残留状态 |
| 重入锁 | 同一 Worker 对同一 Entity 加锁两次 | 记录错误，返回成功（或 panic） |
| 加载超时 | AsyncLoad 超过阈值未返回 | 触发超时事件，消息移入 DLQ |
| Worker Panic | 业务逻辑 panic | recover，消息移入 DLQ，状态恢复 |
| 消息格式错误 | 无法解析消息内容 | 直接移入 DLQ，不重试 |
| Entity 不存在 | 加载时发现 Entity 已被删除 | 返回特定错误，消息处理为"成功"（幂等） |
