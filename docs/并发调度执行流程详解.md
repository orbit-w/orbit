## 2. 思维链一：消息入口的决策树

**场景**：新消息 M 到达 Worker

```
消息 M 到达
    │
    ▼
┌─────────────────────────────────────┐
│ Q1: StagingArea[AnchorID] 存在吗？   │
└─────────────────────────────────────┘
    │
    ├── 存在 ──────────────────────────────────────────────┐
    │   │                                                  │
    │   │  【思考】该 Anchor 有未处理的消息堆积              │
    │   │  可能原因：                                       │
    │   │  - 正在异步加载 Entity (LoadingAnchors=true)     │
    │   │  - 锁竞争失败，等待重试                           │
    │   │                                                  │
    │   │  【决策】保持 FIFO，追加到队尾                     │
    │   │                                                  │
    │   ▼                                                  │
    │  StagingArea[AnchorID].PushTail(M)                   │
    │  return (不执行，等待统一调度)                         │
    │                                                      │
    └── 不存在 ────────────────────────────────────────────┐
        │                                                  │

        │                                                  │

        │                                                  │
        ├── Result_Success ─────────────────────────────── │ ──► 完成
        │                                                  │
        ├── Result_LockBusy ────────────────────────────── │ ──┐
```

## 3. 思维链二：TryProcessAnchor 的完整流程（加锁 + 加载检查）

**场景**：消息 M 涉及 Entity [A, B, C]（已排序）

**核心设计**：先锁后加载（Lock First, Load Later）。锁表独立于 Entity 生命周期，
`TryLock` 可在 Entity 尚未加载时成功（见 `EntityManager.locks` 注释）。
在锁保护下检查加载状态，消除 TOCTOU 竞态。

```
TryProcessAnchor(M) 开始
    │
    │  【关键设计】按固定顺序加锁，避免死锁
    │  排序后: A < B < C
    │
    ══════════════════════════════════════════════════════════════
    │  Phase 1: 加锁序列
    ══════════════════════════════════════════════════════════════
    │
    ▼
┌─────────────────────────────────────┐
│ Step 1: TryLock(A)                  │
└─────────────────────────────────────┘
    │
    ├── 失败 ──► 无需回滚（没有持有任何锁）
    │            M 入 StagingArea[A] 队首
    │            return Result_LockBusy
    │
    └── 成功 ──► 持有锁: {A}
                 │
                 ▼
         ┌─────────────────────────────────────┐
         │ Step 2: TryLock(B)                  │
         └─────────────────────────────────────┘
             │
             ├── 失败 ──► 回滚: Unlock(A)
             │            M 入 StagingArea[A] 队首
             │            return Result_LockBusy
             │
             └── 成功 ──► 持有锁: {A, B}
                          │
                          ▼
                  ┌─────────────────────────────────────┐
                  │ Step 3: TryLock(C)                  │
                  └─────────────────────────────────────┘
                      │
                      ├── 失败 ──► 回滚: Unlock(B), Unlock(A)
                      │            M 入 StagingArea[A] 队首
                      │            return Result_LockBusy
                      │
                      └── 成功 ──► 持有锁: {A, B, C}
    │
    ══════════════════════════════════════════════════════════════
    │  Phase 2: Entity 加载检查（在锁保护下）
    ══════════════════════════════════════════════════════════════
    │
    ▼
┌─────────────────────────────────────────────────┐
│ Step 4: 检查 Entity [A, B, C] 是否全部已加载     │
│                                                 │
│   needLoad := []EntityRef{}                     │
│   for _, ref := range [A, B, C] {               │
│       if !EntityManager.Has(ref) {              │
│           needLoad = append(needLoad, ref)      │
│       }                                         │
│   }                                             │
└─────────────────────────────────────────────────┘
    │
    ├── needLoad 非空 ──► 有 Entity 未加载
    │   │
    │   │  【思考】为什么在持锁后才检查？
    │   │  1. 持锁期间 Entity 加载状态稳定，无 TOCTOU 竞态
    │   │  2. 锁表独立于 Entity 存储，TryLock 不依赖 Entity 是否在内存
    │   │  3. NeedIO 是低频路径（仅首次访问），浪费的锁开销可忽略
    │   │
    │   │  【动作】释放所有锁，触发异步加载
    │   │
    │   ▼
    │  Unlock(C), Unlock(B), Unlock(A)
    │  LoadEntities(M, AnchorID, needLoad)  ← 逻辑单元四
    │  return Result_NeedIO
    │
    └── needLoad 为空 ──► 全部已加载
    │
    ══════════════════════════════════════════════════════════════
    │  Phase 3: 执行业务逻辑
    ══════════════════════════════════════════════════════════════
    │
    ▼
┌─────────────────────────────────────┐
│ Step 5: 执行业务逻辑                 │
│                                     │
│   Execute(M, entities)              │
└─────────────────────────────────────┘
    │
    ▼
Unlock(C), Unlock(B), Unlock(A)
return Result_Success
```

### 3.1 三种结果的完整语义

| 结果 | 触发条件 | 锁状态 | 消息去向 | 后续驱动 |
|------|----------|--------|----------|----------|
| **Result_Success** | 全锁成功 + 全加载 + 执行完毕 | 已全部释放 | 消费完毕 | — |
| **Result_LockBusy** | 某个锁获取失败 | 已全部回滚 | StagingArea 队首 | RetryList |
| **Result_NeedIO** | 全锁成功但有 Entity 未加载 | 已全部释放 | StagingArea 队首（由 LoadEntities 处理） | AsyncComplete 事件 |

### 3.2 设计要点

| 问题 | 答案 |
|------|------|
| 为什么用 Anchor（最小 ID）入队？ | 保证同一组 Entity 的消息总是进入同一个暂存队列，维护 FIFO 顺序 |
| 为什么回滚时释放所有锁？ | 避免持有部分锁导致其他消息饥饿 |
| 为什么入队首而不是队尾？ | 该消息是"正在执行但失败"的，优先级应高于"等待执行"的消息 |
| 为什么在持锁后才检查加载状态？ | 消除 TOCTOU 竞态；锁表独立于 Entity 存储，支持先锁后加载 |
| NeedIO 时为什么要释放锁？ | AsyncLoad 耗时不确定，持锁等待会导致其他 Anchor 饥饿 |
| NeedIO 是否浪费了锁获取？ | NeedIO 仅在首次访问或驱逐后发生（低频），开销可忽略 |

## 4. 思维链三：异步加载的状态流转

**场景**：消息 M 需要 Entity A，但 A 不在内存

```
时间线 ──────────────────────────────────────────────────────────────────►

     T1                    T2                    T3                    T4
     │                     │                     │                     │
     ▼                     ▼                     ▼                     ▼
┌─────────┐          ┌─────────┐          ┌─────────┐          ┌─────────┐
│ 消息 M  │          │ 消息 M2 │          │ AsyncLoad│          │执行 M   │
│ 到达    │          │ 到达    │          │ 完成    │          │执行 M2  │
└─────────┘          └─────────┘          └─────────┘          └─────────┘
     │                     │                     │                     │
     ▼                     ▼                     ▼                     ▼

【T1 状态变化】
LoadingAnchors[A] = false → true
StagingArea[A] = [] → [M]
RetryList 不包含 A
触发 EntityManager.AsyncLoad(A)

【T2 状态变化】
发现 StagingArea[A] 存在
StagingArea[A] = [M] → [M, M2]  // FIFO 追加
不触发新的加载（已在加载中）

【T3 状态变化】
收到 EventAsyncComplete(A)
LoadingAnchors[A] = true → false
Pop M from StagingArea[A]
执行 TryProcessAnchor(M)
  └─ 成功 → StagingArea[A] = [M2] //队列非空，还有M2消息
           RetryList.Add(A)  // 加入重试

【T4 状态变化】（在 RetryProcess 中）
从 RetryList 取出 A
Pop M2 from StagingArea[A]
执行 TryProcessAnchor(M2)
  └─ 成功 → StagingArea[A] = []
           删除 StagingArea[A]
           RetryList.Remove(A)
```

### 4.1 关键设计：LoadingAnchors 与 RetryList 的互斥状态

> 本节从**状态机角度**描述互斥关系和设计原因。
> 对应的**实现检查点**见 [Section 10.2 RetryList 与 StagingArea 的一致性维护](#102-retrylist-与-stagingarea-的一致性维护)——该节列出了在代码中维护 `INV-1` 不变式的 4 个具体位置（LockBusy、NeedIO、AsyncComplete、队列变空）。

在设计中，一个 AnchorID 在同一时刻只能处于以下状态之一：

| 状态 | LoadingAnchors[A] | A ∈ RetryList | 含义 |
|------|-------------------|---------------|------|
| 空闲 | false | false | 无堆积消息 |
| **IO 等待** | **true** | **false** | 正在异步加载，不在重试列表 |
| 锁竞争等待 | false | true | 等待重试获取锁 |

**为什么 NeedIO 时不加入 RetryList？**

LoadEntities（逻辑单元四）会设置 `LoadingAnchors[AnchorID] = true`，并将消息入队首。
（完整流程见 **[Section 11.2](#112-loadentities-逻辑单元四-完整流程)**）

不加入 RetryList 的原因：
1. RetryProcess 遍历 RetryList 时会跳过 `LoadingAnchors[A] == true` 的项——即使加入也会被跳过
2. 如果加入 RetryList，每次 Tick 都会无效遍历这个项，浪费 CPU
3. 等 AsyncComplete 时再加入更高效：此时 `LoadingAnchors` 已清除，消息可以真正被处理

### 4.2 Anchor 状态转换图

```
                    ┌──────────────┐
                    │   空闲状态    │
                    │ StagingArea  │
                    │   为空       │
                    └──────┬───────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
    ┌───────────┐    ┌───────────┐    ┌───────────┐
    │  Success  │    │ LockBusy  │    │  NeedIO   │
    │  直接完成  │    │           │    │           │
    └───────────┘    └─────┬─────┘    └─────┬─────┘
                           │                │
                           ▼                ▼
                    ┌───────────┐    ┌───────────┐
                    │ RetryList │    │ Loading   │
                    │  .Add(A)  │    │ Anchors   │
                    │           │    │  [A]=true │
                    └─────┬─────┘    └─────┬─────┘
                          │                │
                          │                │ AsyncComplete
                          │                ▼
                          │          ┌───────────┐
                          │          │ 处理队首  │
                          │          │ 消息 M    │
                          │          └─────┬─────┘
                          │                │
                          │                │ 队列仍非空？
                          │                ▼
                          │          ┌───────────┐
                          └─────────►│ RetryList │ ← 此时才加入
                                     │  .Add(A)  │
                                     └───────────┘
```

**设计要点**：

| 问题 | 答案 |
|------|------|
| 为什么 IO 等待和锁竞争等待是互斥状态？ | 避免 RetryProcess 无效遍历正在加载的 Anchor |
| AsyncComplete 后为什么要检查队列？ | 加载期间可能有新消息到达，需要继续处理 |
| 为什么 AsyncComplete 后才加入 RetryList？ | 此时 LoadingAnchors 已清除，需要新的调度机制驱动后续消息处理 |

## 5. 思维链四：锁竞争的活锁预防

**场景**：M1 涉及 Entity [A, B]（Anchor=A → Worker1），M2 涉及 Entity [B, C]（Anchor=B → Worker2）。
两条消息因 Anchor 不同被路由到不同 Worker，但共享 Entity B，产生跨 Worker 锁竞争。

> **为什么 Anchor 不同？** 路由规则：`AnchorKey = Sort(EntityRefs)[0]`。
> M1 的 Anchor = min(A,B) = A，M2 的 Anchor = min(B,C) = B。
> 若两条消息 Anchor 相同（如 M1(A,B) 和 M2(A,C) 都以 A 为 Anchor），它们会被路由到同一 Worker 串行执行，不存在锁竞争。

```
        Worker1 (处理 M1(A,B))               Worker2 (处理 M2(B,C))
           │                                    │
           ▼                                    ▼
    TryLock(A) 成功                       TryLock(B) 成功
    持有锁: {A}                           持有锁: {B}
           │                                    │
           ▼                                    ▼
    TryLock(B) 失败                       TryLock(C) 成功
           │                              持有锁: {B, C}
    【回滚】Unlock(A)                          │
    M1 入 StagingArea[A]                       ▼
    return LockBusy                       执行业务逻辑
           │                                    │
           ▼                                    ▼
    ┌─────────────────────────┐          Unlock(C), Unlock(B)
    │ 设置 CooldownSet.Add(A) │
    │ 当前 Tick 跳过 A        │
    └─────────────────────────┘
           │                                    │
           │                                    │
    ═══════│════════════════════════════════════│═══════ Tick 边界
           │                                    │
           ▼                                    ▼
    CooldownSet.Clear()                  处理其他消息
    RetryProcess 取出 A
    TryProcessAnchor(M1)
           │
           ▼
    TryLock(A) 成功
    TryLock(B) 成功 ✓
```

**活锁风险**：若无冷却机制，Worker1 的 RetryProcess 在处理 Anchor A 失败后，
A 仍留在 RetryList 中。若后续迭代或下一次调度再次尝试，会重复
`TryLock(A)✓ → TryLock(B)✗ → Unlock(A)` 的无效循环——每次消耗配额却无进展，
而 Worker2 仍在执行业务逻辑持有锁 B。冷却机制确保 A 在当前 Tick 内不再重试，
留给 Worker2 足够时间释放锁 B。

**设计要点**：

| 问题 | 答案 |
|------|------|
| 为什么需要冷却机制？ | 无冷却时，Worker1 会在 Worker2 持锁 B 期间反复尝试，空转消耗配额形成活锁 |
| 冷却粒度是什么？ | Tick 级别：简单有效，一个调度周期后自动解除 |
| 为什么不用指数退避？ | 游戏服务器对延迟敏感，一个 Tick 的冷却足够让持锁方完成 |
| 为什么竞争的是锁 B 而非锁 A？ | Anchor A 由 Worker1 独占（路由保证），不存在跨 Worker 竞争；只有非 Anchor 的共享 Entity 才会产生跨 Worker 锁冲突 |

## 6. 思维链五：RetryProcess 的配额消耗策略

**场景**：RetryList = [A, B, C, D]，配额 N = 2

```
RetryProcess(Quota=2) 开始
    │
    │  剩余配额: 2
    │
    ▼
┌─────────────────────────────────────┐
│ 遍历 RetryList[0] = A               │
└─────────────────────────────────────┘
    │
    ├── LoadingAnchors[A] == true ──► 跳过 (IO 忙)
    │   剩余配额: 2 (不消耗)
    │
    └── LoadingAnchors[A] == false
        │
        ├── CooldownSet.Contains(A) ──► 跳过 (冷却中)
        │   剩余配额: 2 (不消耗)
        │
        └── 可以处理
            │
            ▼
        Pop M from StagingArea[A]
        TryProcessAnchor(M)
            │
            ├── Success ──► 剩余配额: 1
            │               若 StagingArea[A] 为空，从 RetryList 移除 A
            │
            ├── LockBusy ──► 剩余配额: 1
            │                CooldownSet.Add(A) // 惩罚
            │                M 已回滚到队首
            │
            └── NeedIO ──► 剩余配额: 1
                           LoadingAnchors[A] = true
                           触发异步加载
    │
    ▼
┌─────────────────────────────────────┐
│ 遍历 RetryList[1] = B               │
│ ...同上逻辑...                       │
│ 剩余配额: 0                          │
└─────────────────────────────────────┘
    │
    ▼
配额耗尽，退出 RetryProcess
RetryList[2]=C, RetryList[3]=D 留待下次 Tick
```

**设计要点**：

| 问题 | 答案 |
|------|------|
| 为什么用配额？ | 防止 RetryList 过长时阻塞新消息处理 |
| 配额如何消耗？ | 只在实际执行时消耗，跳过不计数，保证公平性 |
| 遍历顺序是什么？ | FIFO：先入 RetryList 的 Anchor 优先处理 |

## 7. 思维链六：完整的消息生命周期

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           消息 M 的生命周期                                  │
└─────────────────────────────────────────────────────────────────────────────┘

  [诞生]                                                              [死亡]
    │                                                                    │
    ▼                                                                    ▼
 InputChan ──► 消息分发 ──► ProcessAnchor ──┬──► Success ──────────────► 完成
                              │             │
                              │             ├──► LockBusy ──► StagingArea
                              │             │                     │
                              │             │                     ▼
                              │             │              RetryProcess
                              │             │                     │
                              │             │         ┌───────────┴───────────┐
                              │             │         │                       │
                              │             │         ▼                       ▼
                              │             │     Success ──► 完成      LockBusy ──► 冷却
```

## 8. 锁机制的完整实现

### 8.1 锁的数据结构设计

```go
// 全局锁表（跨 Worker 共享）
type GlobalLockTable struct {
    mu     sync.Mutex                    // 保护 locks map 的互斥锁
    locks  map[EntityID]*EntityLock      // EntityID -> 锁状态
}

type EntityLock struct {
    holder   WorkerID      // 当前持有者（0 表示无人持有）
    version  uint64        // 锁版本号（用于调试和监控）
}
```

### 8.2 TryLock 的原子操作流程

```
TryLock(EntityID, WorkerID) -> (success bool)
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│ Step 1: 获取全局锁表的互斥锁                                  │
│         GlobalLockTable.mu.Lock()                           │
└─────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│ Step 2: 检查 EntityLock 状态                                 │
│                                                             │
│   lock := GlobalLockTable.locks[EntityID]                   │
│                                                             │
│   if lock == nil {                                          │
│       // 首次加锁，创建锁记录                                 │
│       lock = &EntityLock{holder: 0, version: 0}             │
│       GlobalLockTable.locks[EntityID] = lock                │
│   }                                                         │
└─────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│ Step 3: 尝试获取锁                                           │
│                                                             │
│   if lock.holder == 0 {                                     │
│       // 无人持有，获取成功                                   │
│       lock.holder = WorkerID                                │
│       lock.version++                                        │
│       GlobalLockTable.mu.Unlock()                           │
│       return true                                           │
│   }                                                         │
│                                                             │
│   if lock.holder == WorkerID {                              │
│       // 【异常】同一 Worker 重复加锁，记录错误                │
│       log.Error("reentrant lock detected", EntityID)        │
│       GlobalLockTable.mu.Unlock()                           │
│       return true  // 或 panic，取决于策略                   │
│   }                                                         │
│                                                             │
│   // 被其他 Worker 持有，获取失败                             │
│   GlobalLockTable.mu.Unlock()                               │
│   return false                                              │
└─────────────────────────────────────────────────────────────┘
```

### 9.3 关键操作的伪代码

```go
// PushHead: 消息入队首（用于回滚和首次入队）
func (sa *StagingArea) PushHead(anchorID AnchorID, msg Message) {
    queue := sa.queues[anchorID]
    if queue == nil {
        queue = &MessageQueue{
            messages: make([]Message, 0, 4),
            createAt: time.Now(),
        }
        sa.queues[anchorID] = queue
    }
    // 在队首插入
    queue.messages = append([]Message{msg}, queue.messages...)
}

// PushTail: 消息入队尾（用于新消息追加，保持 FIFO）
func (sa *StagingArea) PushTail(anchorID AnchorID, msg Message) {
    queue := sa.queues[anchorID]
    if queue == nil {
        // 【异常】不应该发生，记录错误
        log.Error("PushTail to non-existent queue", anchorID)
        sa.PushHead(anchorID, msg)
        return
    }
    queue.messages = append(queue.messages, msg)
}

// PopHead: 消息出队首
func (sa *StagingArea) PopHead(anchorID AnchorID) (Message, bool) {
    queue := sa.queues[anchorID]
    if queue == nil || len(queue.messages) == 0 {
        return Message{}, false
    }
    msg := queue.messages[0]
    queue.messages = queue.messages[1:]
    
    // 队列空了，清理
    if len(queue.messages) == 0 {
        delete(sa.queues, anchorID)
    }
    return msg, true
}

// Exists: 检查队列是否存在且非空
func (sa *StagingArea) Exists(anchorID AnchorID) bool {
    queue := sa.queues[anchorID]
    return queue != nil && len(queue.messages) > 0
}
```

### 10.1 数据结构选择

```go
// 推荐方案 A，游戏服务器场景下 RetryList 通常较短
```

### 10.2 RetryList 与 StagingArea 的一致性维护

> 本节从**实现检查点角度**列出维护一致性的 4 个关键位置。
>
> **设计动机**：IO 等待（`LoadingAnchors[A]=true`）与锁竞争等待（`A ∈ RetryList`）是互斥状态——NeedIO 时刻意不加入 RetryList，原因是 RetryProcess 遍历时会跳过 `LoadingAnchors[A]=true` 的项，若提前加入则每 Tick 都是无效遍历，等 AsyncComplete 后再加入才有实际意义。完整推导见 [Section 4.1 互斥状态原理](#41-关键设计loadinganchors-与-retrylist-的互斥状态)。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    一致性规则 (INV-1)                                    │
│                                                                         │
│   StagingArea[A] 非空  ⟺  A ∈ RetryList  ∨  LoadingAnchors[A] = true   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘

检查点 1: LockBusy 时
┌──────────────────────────────────────────────────┐
│ StagingArea.PushHead(A, M)  // 队列变非空        │
│ if !LoadingAnchors[A] {                          │
│     RetryList.Add(A)        // 加入重试列表      │
│ }                                                │
└──────────────────────────────────────────────────┘

检查点 2: NeedIO 时
┌──────────────────────────────────────────────────┐
│ StagingArea.PushHead(A, M)  // 队列变非空        │
│ LoadingAnchors[A] = true    // 标记加载中        │
│ // 不加入 RetryList，由 AsyncComplete 处理       │
└──────────────────────────────────────────────────┘

检查点 3: AsyncComplete 后队列非空时
┌──────────────────────────────────────────────────┐
│ LoadingAnchors[A] = false   // 解除加载标记      │
│ // 处理完一条后，如果队列仍非空                   │
│ if StagingArea.Exists(A) {                       │
│     RetryList.Add(A)        // 加入重试列表      │
│ }                                                │
└──────────────────────────────────────────────────┘

检查点 4: 队列变空时
┌──────────────────────────────────────────────────┐
│ // 在 PopHead 返回后检查                         │
│ if !StagingArea.Exists(A) {                      │
│     RetryList.Remove(A)     // 从重试列表移除    │
│ }                                                │
└──────────────────────────────────────────────────┘
```

### 10.3 RetryProcess 的完整流程

RetryProcess 的完整遍历逻辑、配额消耗策略和三种结果处理已在
**[思维链五（Section 6）](#6-思维链五retryprocess-的配额消耗策略)** 中以流程图形式详细描述，此处不再重复。

实现时需关注的要点：

1. **迭代器安全**：遍历 RetryList 时可能触发 Remove（Success 后队列空、NeedIO 转移），
   需使用快照迭代或延迟删除，避免遍历中修改问题。
2. **CooldownSet 生命周期**：`cooldownThisTick` 是 RetryProcess 内部的局部 map，
   每次 Tick 调用时新建，调用结束自动销毁，无需跨 Tick 维护。
3. **配额分配**：`RetryQuotaPerTick` 建议初始值设为 10，可根据监控指标动态调整。

## 11.5 思维链七：EntityLoader 内部执行逻辑

> 本节描述 EntityLoader Actor 收到 `EntityLoadBatchRequest` 后的完整内部决策链，
> 以及 `*persistence.LoadResponse` 到达时如何完成 Entity 创建和批次通知。

### 11.5.1 handleLoadBatch 决策树

**场景**：Worker 发送加载请求，Refs = [A, B, C]

```
handleLoadBatch(EntityLoadBatchRequest) 开始
    │
    │  分配批次 ID，创建 pendingBatch{remaining=0}
    │
    ▼
┌────────────────────────────────────────────────────────────────┐
│ 遍历 Refs，对每个 EntityRef 三路分支：                          │
│                                                                │
│   EntityRef A:                                                 │
│   ├── EntityManager.Has(A) == true                             │
│   │       → 跳过（已在内存，无需加载）                          │
│   │         remaining 不变                                     │
│   │                                                            │
│   ├── pendingEntities[A] 存在（A 正在被另一批次加载）           │
│   │       → 追加 batchID 到 pendingEntities[A].batchIDs       │
│   │         remaining++                                        │
│   │         【去重】不重复发起 DB 查询                          │
│   │                                                            │
│   └── 首次请求                                                 │
│           → 解析 database = dbResolver(A.EntityType)          │
│           → 解析 collection = WrapperFactory(A.Type)()        │
│           → pendingEntities[A] = {batchIDs: [batchID]}        │
│           → remaining++                                        │
│           → persistence.AsyncLoad(db, coll, A.ID, self.PID)  │
│             （以 EntityLoader 自身 PID 为 ResponseReceiver）   │
└────────────────────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────────────────────┐
│ 存储 pendingBatches[batchID] = batch                           │
│                                                                │
│ if batch.remaining == 0 {                                      │
│     // 边界：所有 Ref 均已在内存，立即通知 Worker              │
│     completeBatch()  →  ctx.Send(Requester, &EntityLoadBatchComplete{│
│                              AnchorID: req.AnchorID,           │
│                              Success: true,                    │
│                          })                                    │
│ }                                                              │
└────────────────────────────────────────────────────────────────┘
```

**去重机制的并发语义**：

```
时间线 ──────────────────────────────────────────────►

Worker1 发 Batch1 [A, B]   Worker2 发 Batch2 [A, C]
        │                          │
        ▼ T1                       ▼ T2
  handleLoadBatch(Batch1)    handleLoadBatch(Batch2)
  pendingEntities[A] 不存在   pendingEntities[A] 已存在
  → 发起 AsyncLoad(A)         → 追加 Batch2 到 A.batchIDs
  → pendingEntities[A].batchIDs = [Batch1]
                              → pendingEntities[A].batchIDs = [Batch1, Batch2]
                              → 不重复发 DB 查询 ✓

        ▼ T3: LoadResponse(A) 到达
  handleLoadResponse
  → createAndRegisterEntity(A)   // OnLoad + em.Add(A)
  → 通知 Batch1 (remaining--)
  → 通知 Batch2 (remaining--)   // 两个 Worker 都被唤醒
```

**设计要点**：EntityLoader 是单线程 Actor，`pendingEntities` 无需加锁。
多 Worker 的并发请求串行进入 mailbox，天然保证去重操作的原子性。

### 11.5.2 handleLoadResponse 决策树

**场景**：PersistenceActor 返回 `*persistence.LoadResponse`

```
handleLoadResponse(*LoadResponse) 开始
    │
    │  DocumentID → entityID (int64)
    │
    ▼
┌────────────────────────────────────────────────────────────────┐
│ pendingEntities[entityID] 存在？                               │
│   否 → 记录 Warn 日志，return（防御性处理）                     │
│   是 → 继续                                                    │
└────────────────────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────────────────────┐
│ LoadResponse.Error != nil？                                    │
│   是 → loadErr = resp.Error                                    │
│         记录 Error 日志                                         │
│         【注意】Entity 不创建，不调用 em.Add                    │
│                                                                │
│   否 → createAndRegisterEntity(entityID, entityType, resp)    │
│         ├── 文档存在 (Exists=true)：                           │
│         │     entity.OnLoad(resp.Data, isNew=false)           │
│         └── 文档不存在 (Exists=false)：                        │

│               entity.OnLoad(minimal_raw, isNew=true)          │

└────────────────────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────────────────────┐
│ 遍历 pendingEntities[entityID].batchIDs，逐个更新批次：         │
│                                                                │
│   for _, batchID := range pending.batchIDs {                  │
│       batch.remaining--                                        │

│       if batch.remaining == 0 {                               │
│           completeBatch()  →  ctx.Send(Worker, Complete/Error)│

│       }                                                        │
│   }                                                            │
│   delete(pendingEntities, entityID)                            │

```

## 12. Worker 主循环的完整实现

### 12.1 事件类型定义

Worker 是 Actor，事件通过 mailbox 接收，不使用 EventChan。
来自 EntityLoader 的加载完成/失败通知以 `*EntityLoadBatchComplete` 消息形式到达。

```go
// Worker.Receive 中的消息类型分支
switch msg := ctx.Message().(type) {
case *Message:                      // 业务消息（来自路由层）
    w.processMessage(ctx, msg)

case *EntityLoadBatchComplete:      // 异步加载结果（来自 EntityLoader）
    if msg.Success {
        w.HandleEventAsyncComplete(msg.AnchorID)
    } else {
        w.HandleEventAsyncError(msg.AnchorID, msg.Errors)
    }

case *actor.Started:
    // 初始化
case *TickEvent:                    // 定时 Tick（来自定时器 Actor 或 system.After）
    w.onTick()
}
```

### 12.2 主循环伪代码

> 注：Worker 是 Actor，主循环由 Proto.Actor 框架的 mailbox 驱动。
> 以下伪代码保留原有结构用于说明调度逻辑，实际实现为 `Receive` 方法。

```go
func (w *Worker) Run(ctx context.Context) {
    ticker := time.NewTicker(TickInterval)  // 例如 50ms
    defer ticker.Stop()
    
    for {
        select {
        case <-ctx.Done():
            w.shutdown()
            return
            
        case event := <-w.EventChan:
            w.handleEvent(event)
            
        case <-ticker.C:
            w.onTick()
        }
    }
}

// 实际实现为 Actor Receive 方法，以下 handleEvent 仅作逻辑说明
func (w *Worker) handleEvent(msg any) {
    switch m := msg.(type) {
    case *Message:
        w.ProcessAnchor(m)

    case *EntityLoadBatchComplete:
        if m.Success {
            w.HandleEventAsyncComplete(m.AnchorID)
        } else {
            w.HandleEventAsyncError(m.AnchorID, m.Errors)
        }
    }
}

func (w *Worker) onTick() {
    // 阶段 1: 处理重试队列
    w.RetryProcess(RetryQuotaPerTick)  // 例如配额 10
    
    // 阶段 2: 清理过期状态（可选）
    w.cleanupStaleStates()
    
    // 阶段 3: 上报指标
    w.reportMetrics()
}
```

## 14. 状态不变式 (Invariants)

设计正确性依赖以下不变式：

| 不变式 | 描述 | 违反后果 |
|--------|------|----------|
| **INV-1** | `StagingArea[A]` 非空 ⟺ A ∈ RetryList ∨ LoadingAnchors[A] | 消息丢失或重复处理 |
| **INV-2** | LoadingAnchors[A] = true ⟹ EntityLoader 有进行中的批次关联 AnchorID=A | 消息永久阻塞 |
| **INV-3** | 任意时刻，每个 Entity 最多被一个 Worker 持有锁 | 数据竞争 |
| **INV-4** | StagingArea[A] 内消息顺序 = 到达顺序 (FIFO) | 消息乱序 |
| **INV-5** | TryLock 序列严格按 EntityID 升序 | 死锁 |
| **INV-6** | EntityLoader.pendingEntities[ID] 存在 ⟹ 有且仅有一个进行中的 persistence.AsyncLoad(ID) | 重复 DB 查询或响应丢失 |
| **INV-7** | EntityLoader.completeBatch 调用后，pendingBatches[batchID] 必须被 delete | 批次状态泄漏 |

## 15. 边界情况与异常处理汇总

| 场景 | 触发条件 | 处理方式 |
|------|----------|----------|
| 重复 AsyncComplete | Worker 收到两次 EntityLoadBatchComplete (Success=true) | 检查 LoadingAnchors，忽略第二次 |
| 队列意外为空 | PopHead 时队列已空 | 记录警告日志，清理残留状态 |
| 重入锁 | 同一 Worker 对同一 Entity 加锁两次 | 记录错误，返回成功（或 panic） |
| 加载超时 | persistence.AsyncLoad 超过阈值未返回 | EntityLoader 触发超时，发送 Success=false 完成通知 |
| Worker Panic | 业务逻辑 panic | recover，消息移入 DLQ，状态恢复 |
| 消息格式错误 | 无法解析消息内容 | 直接移入 DLQ，不重试 |
| Entity 不存在 | LoadResponse.Exists=false | EntityLoader 合成最小文档，isNew=true，正常 OnLoad |
| Entity 工厂未注册 | GetEntityFactory 返回 nil | EntityLoader 返回 error，批次 Success=false |
| LoadResponse DocumentID 类型异常 | DocumentID 非 int64 | EntityLoader 记录 Error 日志并丢弃响应 |
